# 第三方渠道接入计划

## 背景

当前系统已经有 `channel_account`、`channel_poi_rel`、`channel_room_category_rel`、`distribution_order` 和 `order_main` 等基础表，可以支撑“渠道账号、门店映射、房型映射、渠道订单”的底座。但现有 `/orders/create` 是前台录单接口，要求选择本地具体房间号，不适合直接作为美团、携程等 OTA 平台的下单入口。

美团酒店直连平台公开资料中明确了几类约束：

- 接入方需要能通过接口提供 POI 基本信息、房型、房态信息。
- 订单能力需要符合美团标准下单接口，或者接入方提供标准下单 API 文档供美团开发。
- API 文档包含 POI 同步、房态同步、变更价格、变更库存、订单测试等能力。
- 请求认证使用 HmacSHA1 签名，正式接入需要 partner/clientSecret。
- 上线前需要通过在线自测、联调、测试、上线流程。

所以系统内部不能把美团/携程字段直接写进订单业务，而要先建立统一渠道订单模型，再由各个平台适配器转换。

## 目标状态

第三方平台用户下单后，订单进入系统的链路如下：

```text
美团酒店/美团民宿/携程订单
-> 平台适配器验签并解析原始报文
-> 转成统一渠道订单 DTO
-> 通过渠道账号、外部门店、外部房型映射到本地门店和房型
-> 校验房型库存
-> 创建 PMS 订单
-> 保存原始报文和导入状态
-> 后续同步取消、改期、退款、库存、房价
```

第一阶段先完成“统一渠道订单导入接口”，不直接写真实美团回调，不硬编码美团密钥，不伪造美团正式字段。

## 分阶段实施

### 第一阶段：统一渠道订单导入底座

交付内容：

- 新增内部接口 `POST /channelOrders/import`。
- 请求通过系统网关登录态调用，作为美团/携程适配器转换后的内部入口。
- `channelCode` 必须使用明确渠道编码，例如 `meituan_hotel` 表示美团酒店，`meituan_homestay` 表示美团民宿；不再接受模糊的 `meituan`。
- 请求中的 `channelCode` 必须和 `channel_account.config_json.channelCode` 一致，防止拿一个渠道账号误导入到另一个渠道。
- 根据 `accountId + outPoiId + outRoomCategoryId` 映射本地 `campId + poiId + roomCategoryId`。
- 只支持 `quantity = 1` 的单间房型订单。
- 创建 PMS 订单时不强制选择具体 `roomId`，订单按房型占库存。
- 保存第三方原始报文到 `channel_order_raw`。
- 根据 `accountId + outOrderNo` 做幂等，重复导入返回同一 PMS 订单。
- 订单写入 `order_main`，其中：
  - `channel_id` 存渠道账号 `account_id`，保持现有查询逻辑兼容。
  - `source_type = channel`。
  - `source_label_snapshot` 存渠道名称，如美团、携程。
  - `room_category_id` 存本地房型。
  - `room_id = NULL`，表示尚未排房。
  - `channel_order_no_snapshot` 存第三方原始订单号。

不做内容：

- 不直接对接美团正式回调地址。
- 不实现 HmacSHA1 验签。
- 不支持一单多间房。
- 不实现改期、退款、取消同步。
- 不实现向美团/携程推送库存和价格。

### 第二阶段：真实平台适配器

交付内容：

- 新增 `POST /channelCallbacks/{channelCode}/notify`。
- 按渠道读取 `channel_account.config_json` 中的密钥配置。
- 美团酒店适配器按美团酒店直连规范和 HmacSHA1 验签。
- 美团民宿适配器需要按美团民宿正式文档单独实现，不能假设和美团酒店字段完全一致。
- 携程适配器按携程开放平台规范验签。
- 原始报文转换为统一渠道订单 DTO 后复用第一阶段导入服务。
- 所有验签失败、映射失败、库存不足写入渠道消息日志。

### 第三阶段：渠道订单状态同步

交付内容：

- 支持新订单、取消订单、改期订单、退款/结算状态。
- `accountId + outOrderNo + eventType` 记录事件日志。
- 取消订单时更新 `order_main.status = cancelled` 并释放库存。
- 改期订单必须重新校验库存。
- 失败事件可重试，不能静默吞掉。

### 第四阶段：库存房价出站同步

交付内容：

- PMS 房价修改、开关房、订单占用/释放库存时生成同步任务。
- 同步任务写入 `channel_sync_task`，异步推送到美团/携程。
- 支持失败重试、错误原因、人工重推。
- 遵守平台限流，不在业务接口里同步等待第三方返回。

### 第五阶段：多间房和结算

交付内容：

- 新增或启用订单明细表，例如 `order_room`。
- 一笔第三方订单支持多个房型、多间数量。
- 分销佣金、平台服务费、结算状态进入 `distribution_order` 或独立结算表。
- 建立渠道对账任务。

## 第一阶段接口设计

接口：

```http
POST /channelOrders/import
```

请求示例（美团酒店）：

```json
{
  "channelCode": "meituan_hotel",
  "accountId": "25351",
  "outOrderNo": "MT202606100001",
  "outPoiId": "mt-poi-11001",

  "contactMobile": "13800138000",
```

## 数据库改动

新增表 `channel_order_raw`，用于保存第三方订单原始报文和导入结果。第一阶段保存每个外部订单的最新报文，后续阶段再增加逐事件日志表。

关键唯一约束：

```text
UNIQUE(account_id, out_order_no)
```

注意：当前 `order_main.out_order_no` 是全局唯一，不是 `(channel_id, out_order_no)` 复合唯一。第一阶段会写入内部外部订单键 `accountId:outOrderNo`，并把第三方原始订单号保存到 `channel_order_no_snapshot` 和 `channel_order_raw.out_order_no`。后续应将唯一约束调整为渠道维度唯一。

### 渠道编码约定

| `channelCode` | 渠道名称 | 说明 |
| --- | --- | --- |
| `meituan_hotel` | 美团酒店 | 对应美团酒店直连。 |
| `meituan_homestay` | 美团民宿 | 对应美团民宿，后续按民宿正式文档单独适配。 |
| `ctrip` | 携程 | 后续接携程适配器。 |

`meituan` 不再作为合法渠道编码使用，因为它无法区分美团酒店和美团民宿。

## 风险和限制

- 第一阶段只支持 `quantity = 1`，避免在没有订单明细表前错误表达多间房订单。
- 当前房态页面主要按具体房间展示，`room_id = NULL` 的渠道订单需要后续在房态和排房页继续适配。
- 如果 `accountId:outOrderNo` 超过 `order_main.out_order_no` 的 64 字符限制，接口会明确失败，不做截断或隐式 hash。
- 真实美团/携程接入必须使用正式平台文档和测试账号，不能只按公开页面猜字段。

## 验证计划

- 新增集成测试：渠道订单导入成功后生成 `order_main`，且 `room_id` 为空。
- 新增集成测试：美团酒店和美团民宿分别保存不同 `channel_order_raw.channel_code`。
- 新增集成测试：传入旧 `meituan` 编码时明确失败。
- 新增集成测试：重复导入同一 `accountId + outOrderNo` 返回同一 PMS 订单，不重复创建。
- 新增集成测试：外部房型未映射时明确失败，不创建订单。
- 运行 `mvn -pl zp-service-order -Dtest=ChannelOrderImportIT test`。
